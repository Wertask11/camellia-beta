# Camellia 統合品質改善・正式リリース準備
## 壁打ち①〜⑫・⑭〜⑯ 全採用方針の実装指示書

### 対象

Repository：`Wertask11/camellia-beta`

Production：https://camellia-beta.vercel.app/

サービス：Camellia

対象：18〜45歳の女性向けウェルビーイングサービス。スマートフォン中心。

---

# 0. 最重要指示

今回の目的は、これまでの壁打ちで採用した設計方針を、既存のCamelliaへ正確に反映し、品質を改善することである。

**一部だけを実装して完了と報告してはならない。**

ただし、すべてを一度に無計画に変更することも禁止する。

以下の順番で作業すること。

1. 現在のリポジトリとProductionを調査する。
2. 既存機能・仕様・データ構造・料金・認証・権限を把握する。
3. 本指示書の採用事項を1件ずつ照合する。
4. 実装済み・部分実装・未実装・不具合・未決定を分類する。
5. 依存関係とリスクを整理する。
6. 既存機能を壊さない順序で実装・改善する。
7. 単体・統合・E2E・権限・プライバシーのテストを行う。
8. 実際のスマートフォン表示と利用導線を検証する。
9. 実装結果と未解決事項を証拠付きで報告する。

実装は小さな単位で進め、各段階でテストを通すこと。

**未決定事項をCodexが勝手に決定してはならない。**

本番公開、料金徴収開始、紹介キャンペーン開始、ユーザーへの通知配信など、運営上の開始判断は開発完了とは分離する。

既存の利用者データ、投稿、Memory、Reflection、Check、Circle、Place、My Tree、認証情報、課金状態を保護する。

# 1. 壁打ち①：Todayのおすすめ表示

採用方針：

**おすすめ1件を中心に提示し、他の選択肢も残す。**

実装要件：

- Todayの中心に、その日の利用者に合いそうな提案を1件提示する。
- おすすめ理由を分かりやすく表示する。
- 別の候補を見る方法を残す。
- 1件しか選べない構造にしない。
- おすすめを利用しなくてもTodayを使える。
- 既存のCheck、Recommendation、Action、Reflectionとの関係を保護する。
- データ不足時のフォールバックを用意する。
- AIの提案を断定的な診断として表示しない。

完了条件：

利用者がTodayを開き、中心提案を確認し、必要なら他の候補を選べること。

---

# 2. 壁打ち②：自動提案と本人による調整

採用方針：

**自動提案＋本人調整。**

実装要件：

- Camelliaが候補を提案する。
- 利用者自身が希望や条件を調整できる。
- 調整結果を反映した候補を提示する。
- 自動提案を強制しない。
- 個人的なデータの利用範囲を明示する。
- 無料プランの提案品質を意図的に低下させない。
- 有料プランでは個別化、比較、提案の深さなどで価値を高める。
- 無料でも実用的な体験を成立させる。

---

# 3. 壁打ち③：Plusの中心価値

採用方針：

**Plus最大の価値はパーソナル提案。Placeとの連携を重視する。**

実装要件：

- Freeでも基本的なおすすめを利用できる。
- Plusでは、本人が許可した好みや過去の行動を活かした、より個別化された提案を目指す。
- 提案理由と候補比較を分かりやすくする。
- Placeの店舗・体験提案を重要な対象にする。
- 個別化のために無制限に個人情報を収集しない。
- PlusでなければCamelliaの中心体験が成立しない設計にしない。
- 実際のAI原価と利用制限を確認する。

---

# 4. 壁打ち④：Plusの追加価値

採用方針：

**提案品質の向上＋提携店舗特典。**

実装要件：

- Plusの提案品質と個別化を強化する。
- Placeの提携店舗が提供する特典を扱える構造を整える。
- 特典の提供は店舗の任意とする。
- 特典が存在しない店舗でもPlaceに参加できる。
- 提供条件、対象者、有効期限などを正確に表示する。
- 特典が未提供の場合、架空の特典を表示しない。
- 特典の有無だけでおすすめの適合性を歪めない。

---

# 5. 壁打ち⑤・⑥：提携店舗の料金と参加条件

採用方針：

- 初期は無料実証。
- 基本掲載は無料。
- 提携店舗特典は任意。
- 実績を確認した後に有料サービスを検討する。

実装要件：

- 基本掲載と有料オプションを区別する。
- 無料店舗でも適切なおすすめ対象になる。
- 店舗が追加料金を明示的に承認しない限り課金しない。
- 無料契約を自動的に有料契約へ移行しない。
- 店舗情報の更新・停止・公開管理を安全に行えるようにする。
- 料金制度の未決定部分は保留する。

---

# 6. 壁打ち⑦・⑧：Placeの対象者と初期店舗

採用方針：

**中心利用者は、自分に合う場所や体験を探す女性。**

初期店舗は以下の4分野を同等に扱う。

1. カフェ・飲食店
2. 美容
3. リラクゼーション
4. 体験サービス

実装要件：

- 特定の1ジャンルだけを優遇しない。
- 利用者の希望や利用条件を優先する。
- 店舗数が少なくても使える設計にする。
- 該当店舗がない場合は、存在しない店舗を生成しない。
- 実在しない提携店舗を表示しない。
- 店舗情報と提携状況を区別する。

4分野の同等展開は事業方針であり、実際の店舗数を無理に均等にすることを意味しない。

# 7. 壁打ち⑨：登録前の体験

採用方針：

**登録前にもCamelliaの価値を体験できる。**

登録前に伝える内容：

- Checkがどのような体験なのか
- 具体的な提案の例
- Placeの店舗名・写真・おすすめ理由
- 登録後に利用できる機能
- Plusで広がる価値

実装要件：

- ログイン不要の体験・紹介ページを整える。
- 登録前にCamelliaの価値が分かるようにする。
- 公開可能な情報と個人データを厳密に分離する。
- Checkの例示にはデモデータを利用し、他人の実データを公開しない。
- 個人のCheck、Memory、Reflectionはログインなしで取得できないようにする。
- 登録は既存のLINE・Google認証へ接続する。
- 未認証者向け公開体験と、認証必須の個人機能を混同しない。
- 既存の認証・アカウント統合・利用資格に関する仕様を保護する。

# 8. 壁打ち⑩：Camelliaのキラー体験

採用方針：

**「今日の私に合うPlaceが見つかる」**

中心となる循環：

Check → Recommendation → Place / Discover → Action → Reflection

実装要件：

- Todayから提案を確認できる。
- 提案からPlaceやDiscoverへ自然に移動できる。
- 店舗・体験を発見した後、次の行動が明確である。
- 実際に体験した後、任意でReflectionにつなげられる。
- Checkを毎回強制しない。
- 登録前・Free・Plusで、できることを正確に説明する。
- Plusでは本人の許可を得た個別化や比較機能を強化する。
- 無理な回遊や長時間利用を目的にしない。

# 9. 壁打ち⑪：Placeの信頼性

採用方針：

**掲載前に店舗の実在・掲載許可・情報を確認する。**

実装要件：

- 店舗の実在確認
- 掲載許可の管理
- 店舗情報の確認
- 営業時間・料金・所在地・予約方法の管理
- 店舗情報の更新履歴
- 掲載停止・非公開管理
- 広告料金による不当な推薦順位操作の防止
- 体験重視のレビュー・感想機能の段階的整備
- 店舗の自己紹介と利用者の体験談を区別
- 虚偽情報・不適切投稿への対処

実在確認前の店舗を、確認済み提携店舗として表示しない。

# 12. 壁打ち⑭：女性がCamelliaを使い続ける理由

採用方針：

**記録を続けるためではなく、今日の自分に合う何かが見つかるから開く。**

## 12-1. Today

- その日の自分に合う提案を届ける。
- Checkを強制しない。
- 利用しなかった日を責めない。
- 連続利用日数によるプレッシャーを設けない。
- 次の発見につながる体験を優先する。

## 12-2. Circle → Place

採用方針：

**CircleからPlaceへの発見を優先する。**

- Circleの投稿から関連Placeへ移動できる。
- 投稿者がPlaceを手動で選んで紐づける。
- AIによる自動紐づけを前提にしない。
- 投稿者の意思なく店舗情報を付与しない。

## 12-3. 店舗のCircle投稿

採用方針：

**店舗はPlaceに紐づくイベント・体験に限って投稿可能。**

- 一般女性の投稿と店舗投稿を区別する。
- 店舗による無関係な広告投稿を認めない。
- 投稿権限をサーバー側で検証する。
- 店舗の宣伝が通常の体験共有を圧迫しないようにする。

## 12-4. Circleの表示

採用方針：

**新着投稿＋Today連動のおすすめ。**

- 新着順で投稿を見られる。
- Todayに関連する投稿を提案できる。
- CheckをしなくてもCircleを利用できる。
- 個人情報を無断で推薦に使用しない。
- 新着とおすすめの違いを分かりやすくする。

## 12-5. 通知

採用方針：

**本人に合うパーソナライズ通知。**

- 通知は本人の選択に基づく。
- 通知の種類・頻度を制御できる。
- 不必要な通知を送らない。
- Checkやセンシティブな内容をロック画面に露出させない。
- 通知の拒否や停止によって基本機能を制限しない。

## 12-6. KPI

最重要KPI：

**利用者本人が感じた体験価値。**

補助KPI：

- 7日後の継続利用
- 30日後の継続利用
- CircleからPlaceへの行動
- Place詳細の閲覧
- 実際の利用体験に関するフィードバック

単純な滞在時間や通知開封数だけを成功指標にしない。

# 13. 壁打ち⑮：女性が誰かに紹介したくなる理由

採用方針：

**Placeの発見とCamelliaでの個人的な体験の両方を共有できる。**

## 13-1. 共有機能

- Placeを共有できる。
- Camelliaの体験を本人の意思で共有できる。
- 公開対象を本人が選ぶ。
- Check、Memory、Reflectionの原本を自動公開しない。
- 共有前に内容を確認できる。
- 公開後の共有停止・削除を検討する。
- 共有リンクからログイン不要の専用ページを開ける。
- 共有ページからLINE・Google登録へつなげる。
- 共有ページに秘密情報や認証トークンを含めない。

## 13-2. 紹介特典

紹介された新規利用者：

**Plus 7日間体験。**

紹介者：

**My Treeの限定装飾。**

付与条件：

**紹介された人の新規登録完了。**

紹介者の報酬上限：

**月3件。**

## 13-3. My Treeの特典

- 紹介成立ごとに好きな装飾を1つ選べる。
- 月3件まで。
- 獲得した装飾は永久保有。
- Free・Plusどちらでも利用できる。
- 木の成長スコアや評価には影響しない。
- 紹介人数ランキングを作らない。
- 他人と競わせない。
- 装飾の具体的な種類は未決定。

## 13-4. Plus体験の安全性

- 7日間で終了する。
- 自動課金しない。
- 原則1人1回。
- 既存の無料体験と不正に重複させない。
- 通常Plusとの機能差がある場合は明示する。
- AI利用には体験専用の上限を設ける。
- 利用者に分かる形で制限を説明する。

## 13-5. 不正対策

- 自己紹介を禁止する。
- 同一人物の重複特典取得を抑止する。
- LINEとGoogleの別アカウントによる重複に注意する。
- 不自然な大量登録を検知する。
- 不正の疑いだけでアカウントを削除しない。
- Check、Memory、Reflectionの内容を不正判定に利用しない。
- 端末指紋や本人確認書類の強制収集を安易に導入しない。

## 13-6. 費用管理

採用方針：

**月間予算上限＋Plus体験のAI利用枠。**

- 月間キャンペーン予算を設定できる構造にする。
- 1人当たりのAI利用原価を制御する。
- 予算上限に達したら新規特典受付を停止する。
- 既に付与した有効な特典は原則維持する。
- AI原価の異常増加を検知する。
- 重大な不正や個人情報漏えいが発生した場合、影響範囲を停止できるようにする。

## 13-7. 開始時期

採用方針：

**紹介制度はCamellia正式リリース後に開始する。**

開始条件：

- 利用者の体験価値を確認できている。
- 継続利用を把握できている。
- 特典付与が正確に機能する。
- 不正対策が機能する。
- AI原価と月間予算を管理できる。
- 個人情報保護と安全性を確認できている。

**紹介機能のコードが完成しても、キャンペーンを自動開始しないこと。**

機能フラグ等で安全に無効状態を維持できる設計にする。

## 13-8. 未決定事項

以下は勝手に決めない。

- 月間予算の具体的金額
- Plus体験専用AI利用枠の数値
- 紹介開始の数値基準
- My Tree装飾の具体的なデザイン
- 月3件超過時の新規利用者側特典の扱い
- 既存Plus体験との詳細な重複ルール
- 紹介キャンペーンの実施期間

未決定事項がないと安全に完成できない部分は、実装可能な基盤と未決定部分を分離する。

# 14. 壁打ち⑯：Camellia Placeを実際に訪れたくなる場所にする

## 14-1. Placeの中心価値

採用方針：

**今の自分に合う場所が見つかる。**

- 店舗名を並べるだけのサービスにしない。
- その店舗でどんな時間を過ごせるかを伝える。
- 利用者の希望と店舗の実際の特徴を結びつける。
- 気分や希望を本人が直接選択できる。
- Checkの実施を必須にしない。

## 14-2. 初期店舗構成

採用方針：

**異なるジャンルを少数ずつ集める。**

対象：

- カフェ・飲食店
- 美容
- リラクゼーション
- ワークショップ・体験サービス

特定ジャンルの店舗数確保を正式リリースの絶対条件にしない。

## 14-3. 店舗への中心価値

採用方針：

**新規顧客・再来店・体験集客を一体で支援。**

段階的に、

1. 店舗を知ってもらう
2. 来店や予約につなげる
3. 次の利用や再発見につなげる

という関係を目指す。

集客成果を保証する表現は使わない。

## 14-4. 店舗参加条件

採用方針：

**基本情報＋体験紹介を必須、限定企画は任意。**

必須：

- 店舗の基本情報
- 正確な所在地
- 料金・価格帯
- 営業時間
- 予約・問い合わせ方法
- 提供しているサービスや体験
- どんな過ごし方ができるか

任意：

- Camellia限定メニュー
- 限定体験
- ワークショップ
- イベント
- 優待
- Circleでのイベント告知

店舗に無理な割引や赤字提供を要求しない。

## 14-5. 来店導線

採用方針：

**店舗の既存導線を基本に、必要な店舗だけ追加機能。**

基本：

- 地図
- 公式サイト
- 公式予約ページ
- 問い合わせ
- 電話などの既存連絡手段

追加機能：

- 希望店舗向けのイベント申込み
- 希望店舗向けの来店確認

既存の予約システムを置き換えることを必須にしない。

## 14-6. 成果計測

採用方針：

**オンライン計測＋希望店舗のみ来店確認。**

基本計測：

- 店舗詳細の閲覧
- 地図への遷移
- 予約リンクのクリック
- 問い合わせリンクのクリック

希望店舗のみ：

- QRコード等による来店確認
- 確認可能な再来店の計測

重要：

**クリックを来店として報告してはならない。**

確認できた成果と推測を分離する。

店舗向けデータは原則として集計値を使用する。

## 14-7. 収益モデル

採用方針：

**基本無料＋有料オプションを段階的に導入。**

Phase 1：

基本掲載・体験紹介・既存予約導線・基本的な成果集計を無料で提供する。

Phase 2：

店舗が追加料金を払う価値のある機能を検証する。

Phase 3：

実績と原価を確認した後、有料サービスを拡大する。

有料掲載と通常のおすすめは明確に区別する。

## 14-8. Placeのおすすめ基準

採用方針：

**利用条件で絞り、気分・希望でおすすめする。**

利用条件：

- 距離・エリア
- 予算
- 営業時間
- 予約の要否
- 利用可能なサービス・体験

その後：

- 今どんな時間を過ごしたいか
- 本人が選んだ希望
- 本人が許可した好み

などを基準に提案する。

必須条件を勝手に緩めない。

該当店舗がない場合は、条件に合う店舗がないことを正直に伝える。

おすすめ理由を表示する。

店舗情報の事実とAIの推測を区別する。

広告料金による不当な順位操作をしない。

## 14-9. 来店後の体験

採用方針：

**Memory・Reflection・Circleを本人の意思でつなぐ。**

Memory：

個人的な思い出として記録する。

Reflection：

どんな体験が心地よかったかを振り返る。

Circle：

本人が希望した場合だけ体験を共有する。

- すべて任意。
- 来店による自動投稿を禁止。
- Circle投稿へのPlace紐づけは本人が手動選択。
- Reflectionの内容を推薦に利用する場合は本人の許可を得る。
- 記録しない人を不利に扱わない。
- 来店未確認の場合に「訪問済み」と断定しない。
- 公開投稿から正確な行動履歴や現在地が漏れないようにする。

## 14-10. 壁打ち⑯でまだ決まっていないこと

次の事項は、まだ採用決定されていない。

- Place正式リリースに向けた完成目標のA/B/C
- 初期提携店舗への具体的な営業方法
- 店舗数に関する最終合格基準
- 店舗向け有料オプションの料金
- 来店確認機能の具体的な実施方式

これらをCodexが勝手に確定しないこと。

# 16. セキュリティ・プライバシー

必須事項：

- 認証と認可を分離して検証する。
- Firestore等のアクセス制御をサーバー側で強制する。

- 店舗管理者が他店舗の情報を変更できないことを確認する。
- 紹介特典の二重付与を防止する。
- 特典付与処理の冪等性を確保する。
- AI利用枠はUIだけでなくサーバー側で制御する。
- APIのレート制限を検証する。
- ログに個人の機微な内容を不要に保存しない。
- 計測イベントにCheck本文などを送信しない。
- 共有リンクから非公開データへアクセスできないようにする。
- 通知に機微情報を含めない。
- 未成年利用・対象年齢・AI利用条件の現行規約を確認する。

個人データを推薦へ利用する場合は、目的・同意・撤回方法を明確にする。

# 18. 実装の進め方

以下の工程に分割する。

### Phase 0：現状監査

全機能・全決定事項の対応表を作成する。

各項目を次の5段階で分類する。

- 完了
- 部分実装
- 未実装
- 不具合
- 未決定・要確認

コード、テスト、画面、権限、Productionの確認結果を根拠として示す。

### Phase 1：Today・推薦・Plus

壁打ち①〜④・⑩の中心体験を改善する。

### Phase 2：Placeの基本品質

店舗データ、掲載審査、検索、推薦、詳細表示、外部予約導線を改善する。

### Phase 3：Circle・Memory・Reflection連携

壁打ち⑭・⑯の体験循環を改善する。

### Phase 4：店舗向け管理・計測

店舗の掲載管理、成果集計、任意の来店確認基盤を整える。

### Phase 5：共有・紹介制度

ログイン不要の共有ページを整える。

紹介特典は、未決定事項を保留した安全な構造まで実装する。

紹介キャンペーンは正式リリース後の開始条件が満たされるまで無効状態を維持する。

### Phase 6：総合品質検証

スマートフォンE2E、認証、権限、データ保護、原価管理、既存機能の回帰テストを行う。

各Phaseで完了条件を定義し、テスト失敗を放置して次へ進まないこと。

# 20. 完了の定義

完了とは、単にコードを書いた状態ではない。

採用済みの決定事項について、

1. 仕様との一致が確認できる。
2. 既存機能が保護されている。
3. 権限・プライバシーが安全である。
4. スマートフォンで実際に操作できる。
5. 主要なテストが通過している。
6. 未決定事項が勝手に確定されていない。
7. 本番で有効な機能と、未公開の機能が明確に区別されている。

この状態を目指す。

まずPhase 0の監査から開始し、採用事項の全件対応表を作成すること。

その後、依存関係に従って実装・改善を進める。

**作業を途中で打ち切って全体完了と報告してはならない。**

ユーザーによる判断が必要な事項は、選択肢・推奨案・影響を整理して確認すること。

Camelliaの価値は、女性をアプリに長時間滞在させることではない。

**今日の自分に合う何かを見つけ、現実の生活を少し豊かにできること。**

すべての改善は、この価値につながっているかを基準に判断すること。
