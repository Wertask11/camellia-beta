## 0. 最重要指示

対象リポジトリ：
`Wertask11/camellia-beta`

Production：
https://camellia-beta.vercel.app/

正式リリース予定日：
**2026年12月1日**

今回の目的は、Camelliaを12月1日に正式リリースできる状態まで完成させること。

**実店舗の確保・契約と、決済事業者の契約・審査を除くすべての必要な機能・運用基盤を完成させる。**

ただし、Placeへの実店舗導入とPlusの決済処理の開発は並行して進める。

以下を厳守すること。

1. 調査・監査・計画書作成だけで作業を終えない。
2. 既存コードを最大限活用し、未完成部分を実装して完成させる。
3. 機能を削除・簡略化して完成扱いにしない。
4. 外部サービスの契約や本人の承認が必要な事項は捏造しない。
5. 外部依存があっても、依存しない作業は最後まで完成させる。
6. 未決定の料金・予算・利用上限などを勝手に確定しない。
7. 本番データ、既存アカウント、過去の記録を保護する。
8. Productionへのデプロイ、課金開始、機能公開は明示的な承認なしに実行しない。
9. すべての変更はテストと検証証拠を残す。
10. 12月1日の正式リリースを最優先し、不要な新機能の追加は行わない。

- Check

## B. Today / Discover / Camellia AI

正式リリースに必要な品質まで改善する。

- Todayの中心提案
- Checkなしでも利用できる導線
- 本人による条件調整
- Discoverの提案精度
- 選択した行動の保存

現在のプレビューのみの状態から、正式に共有できる完成形まで実装する。

共有URLの発行から第三者の閲覧、取消後のアクセス拒否まで実際に検証する。

## D. 紹介機能を完成させる

既存の決定事項を維持する。

- 紹介リンク
- 紹介された人の登録
- 新規登録成立の判定
- Plus 7日間体験
- 自動課金なし

- 月3件まで
- 獲得装飾は永久保有
- 競争・ランキングなし

未完成部分をすべて実装する。

特に以下を必須とする。

1. 新規登録完了hookとの接続
2. 紹介コードと本人確認済みアカウントの関連付け

9. 月間上限管理
10. キャンペーン停止・再開
11. 予算と原価の管理
12. 不正利用への対応

登録不要の「無料利用開始」と、特典対象となる「本人確認済みCamellia ID取得」を混同しない。

月予算・専用AI枠・キャンペーン期間など、未決定の事業数値は設定可能な状態まで実装し、承認待ちとして報告する。

# 3. Placeの完成

PlaceはCamelliaの中心価値である。

**「今の自分に合う場所や体験が見つかる」ことを最重要の受入条件とする。**

実店舗の確保は運営側で並行して行う。

Codexは、店舗が確保された時点で速やかに公開できる状態を完成させる。

必要機能：

- 店舗情報登録
- 店舗の実在確認
- 掲載許可・写真許可の記録
- 下書き
- 審査
- 公開
- 更新
- 停止
- 店舗担当者権限
- 運営管理画面
- 店舗詳細
- エリア・予算・時間・希望による検索
- おすすめ理由
- Place比較
- お気に入り保存
- 公式サイト・予約・地図への導線
- 任意の体験記録
- Memory / Reflectionとの連携
- Circleとの連携
- 店舗別の閲覧・外部導線計測

店舗募集から掲載申請までの入口も整備する。

基本掲載無料の方針を維持し、有料オプションは勝手に開始しない。

既存のデモ3件を実店舗として扱わない。

実店舗の掲載目標は、初期の4分野に対応する4店舗を提案値とする。店舗数は最終的に運営が承認する。

実店舗の情報・許可が届く前に、架空データで本番公開を成功扱いにしない。

# 4. Plusと決済処理を並行して完成させる

Plusの月額料金は500円。

決済事業者の契約・審査は運営側の外部準備とする。

Codexは、契約以外の技術実装を並行して完成させる。

## A. Plusの提供価値

既存仕様を確認したうえで、以下を完成させる。

- 本人の希望に基づく個別化
- Placeの高度な比較
- Plus専用機能の権限制御
- 無料とPlusの機能差の明示
- Plusの会話機能・利用上限の仕様整理
- 紹介による7日体験との整合
- 店舗特典がない場合の適切な表示

未決定のAIモデル・回数・文脈範囲は、原価と既存仕様を確認して提案し、承認を求める。

未提供の機能を料金ページで宣伝しない。

## B. 決済処理

既存の決済関連コードを確認する。

利用する決済事業者が既に決定・設定済みなら、その方式を優先する。

未決定の場合は、特定事業者へ勝手に本番契約するのではなく、決済処理を分離した安全な構成で実装する。

必要機能：

1. Plus購入画面
2. 月額500円のサブスクリプション
3. 決済セッション作成
4. サーバー側の決済結果検証
5. Webhook署名検証
6. 重複Webhookの冪等処理
7. Plus権限付与
8. 更新・決済失敗
9. 解約
10. 返金
11. 権限失効
12. 紹介体験との重複処理
13. 決済履歴
14. 利用者への料金・更新条件の表示
15. 管理者による状態確認
16. 障害時の復旧
17. 監査ログ
18. テスト環境での一連の決済検証

決済成功をフロントエンドの自己申告だけで確定しない。

決済事業者の秘密鍵はサーバーのみで管理する。

本番事業者の接続が未完了なら、その状態を明確に報告し、課金受付は開始しない。

# 7. 開発工程とPR

以下の工程を並列化できるよう、依存関係を整理する。

### Workstream 1：無料利用・ID・AI・記録
既存の基礎機能を正式リリース品質まで完成。

### Workstream 2：共有・紹介
共有の実公開と紹介特典の接続を完成。

### Workstream 3：Circle・通知
Circleの正式公開準備、Place連携、通知配信を完成。

### Workstream 4：Place
店舗登録・審査・公開・管理・検索・計測を完成。

### Workstream 5：Plus・決済
Plusの提供価値、権限、決済処理を完成。

### Workstream 6：セキュリティ・統合試験
各Workstreamの変更を統合し、正式リリース条件を検証。

作業の衝突を避けるため、担当ファイルと依存関係を明確にする。

PRはレビュー可能な単位で作成する。

一つのPRに無関係な大規模変更を混在させない。

各PRでlint、typecheck、unit、emulator、build、必要なブラウザ試験を実行する。

既存テストの削除・無効化でPASSにしない。

# 8. 完成判定

次のすべてを確認する。

| 機能 | 完成条件 |
|---|---|
| 無料利用 | 登録なしで基本機能が実際に利用できる |
| Camellia ID | 認証・引き継ぎ・同期・削除が成功 |
| Today / AI / Discover | 実API・実ブラウザで主要導線が成功 |
| 共有 | 発行・閲覧・取消・失効が成功 |
| 紹介 | 登録→7日体験→装飾付与が成功 |
| Circle | 投稿・交流・通報・運営対応が成功 |
| Circle × Place | 本人選択の店舗連携が成功 |
| 通知 | 対応環境で実配信・停止が成功 |
| Place | 実店舗を安全に登録・審査・公開できる |
| Plus | 仕様どおりの機能と権限制御が成功 |
| 決済 | テスト決済から解約・失効まで成功 |
| 安全性 | 権限・個人情報・原価・削除の検証成功 |
| Production | 本番条件で実受入が成功 |

**完成の定義は「コードが存在すること」ではない。**

機能が実際につながり、利用でき、必要なテストを通過し、運営が受け入れられる状態を完成とする。

外部依存で本番実証できない項目は、完成とせず「外部準備待ち」と明記する。
